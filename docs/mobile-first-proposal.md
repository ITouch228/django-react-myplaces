# Вариант развития: мобильный MyPlaces с offline-first хранением

Статус: **архитектурное предложение для обсуждения**, не принятое решение о переписывании приложения. Текущая версия остаётся Django + React Web. Предложение основано на существующих мобильных клиентах MyInventory и MyFiles (Expo/React Native, локальная SQLite).

## Цель

Вести места, посещения, чеки, позиции и оценки на смартфоне **без сервера и интернета**. Доступность ПК/домашнего сервера должна влиять только на возможность синхронизации. Не вводить обязательную авторизацию для работы с локальными данными.

## Целевая схема

```text
Android (Expo / React Native)
  ├── экраны: карта, мои места, карточка места, чеки, настройки
  ├── expo-location (разрешение foreground по действию)
  ├── expo-sqlite: Place / Check / CheckItem / SyncOutbox
  └── SyncService (в будущем, необязательно)
          │ LAN / HTTPS API + токен
          ▼
       Django / DRF -> PostgreSQL (по мере готовности сервера)
```

Основное приложение должно полноценно работать при отключённом интернете; **онлайн-зависимая карта** требует отдельного решения по офлайн-тайлам или явного указания, что подложка карты может отсутствовать, а сохранённые данные останутся доступны.

## Модель идентификаторов

Для каждого места/чека/позиции **client-generated UUID**, не меняющийся на протяжении жизни записи. Серверные integer ID, если нужны для старого DRF, хранятся **отдельно** в таблице сопоставлений `sync_mappings(entity, local_uuid, server_id)`. При синхронизации не переписывать локальные первичные ключи и внешние ссылки.

Поля: `id (UUID)`, `updated_at`, `deleted_at` (tombstone), `sync_version`/серверная ревизия. Для денег фиксированное число копеек как целое или строго определённый decimal-string; нельзя использовать JS float для расчётов сумм.

## Отправка изменений

1. В одной SQLite-транзакции сохранять объект и запись `sync_outbox(op_id, entity_type, entity_uuid, action, payload, created_at, status)`.
2. При доступности сервера отправлять операции по устойчивому `op_id` с идемпотентностью: повтор запроса после таймаута не создаёт дубль.
3. Сервер возвращает сопоставление UUID ↔ server ID, ревизию и изменения с момента `sync_cursor`.
4. Клиент применяет изменения транзакционно, обновляет отображение и отмечает операции доставленными.
5. Удаление синхронизируется через tombstones. Конфликты разрешать по правилам **каждой сущности**. Для двух устройств не полагаться исключительно на `updated_at` часов телефона.
6. Поддержать восстановление и экспорт локальной БД, миграции схемы и тесты повторной отправки после сбоя сети.

## Границы

- Не переносить весь существующий React/Leaflet JSX в RN механически: переносить бизнес-правила и контракты, UI строить на нативных компонентах.
- Не переносить существующие серверные integer ID на место главного клиентского UUID.
- Не выключать существующий веб-клиент и не удалять Django, пока не решены импорт старых пользовательских данных и резервное копирование.
- Один общий Jenkins агент можно использовать для проверок Expo без постоянной Android APK сборки, как в MyInventory.
- Потребность в полностью офлайн-карте, облачной синхронизации и поддержке нескольких пользователей решать отдельно до разработки M3/M5.
