# Дорожная карта MyPlaces

## Цель проекта

MyPlaces помогает сохранять заведения, находить их на карте, записывать визиты, блюда, оценки и расходы. Основной сценарий проходит с телефона: открыть сохранённое место, занести чек и потом найти, где был и сколько заплатил. Дневник должен сохранять данные при обновлении и восстанавливаться на чистой установке.

Сначала доводим рабочую версию Django + React до надёжного личного релиза. Возможность вести дневник вне домашней сети проверяем отдельно. [Мобильный клиент на Expo с локальной SQLite](mobile-first-proposal.md) остаётся архитектурным предложением.

## Исходное состояние

Срез от 26.11.2026, `main` на коммите `92518cf`.

- Django REST Framework и SQLite хранят личные места, чеки и их позиции. Есть JWT, разделение данных по владельцу, проверка координат и цен. Карта использует Leaflet, OpenStreetMap и Nominatim.
- В веб-клиенте есть адаптивная панель мест, поиск и сортировка, меню аккаунта, выбор и редактирование координат места, стартовое позиционирование карты и закрываемое уведомление о геолокации. Создание и редактирование существующего места работают в `main`.
- В `main` место ещё без категории, избранного и отметки «Хочу посетить». Чек содержит цены позиций без отдельного количества. Эти изменения находятся в рабочих ветках.
- На проверенном коммите локально прошли 49 тестов Django, 58 тестов фронтенда и сборка Vite. Jenkinsfile проверяет backend, frontend и MkDocs. CORS с опубликованным портом и полный запуск Compose требуют отдельной проверки.
- `README.md`, примеры окружения и Compose указывают разные порты. Compose публикует веб-клиент на `8073`, API на `8072` и документацию на `8071`. Пример CORS разрешает `8071`, поэтому с ним браузер блокирует вход с `8073`.

### 0. Починить запуск и проверить бэкап { #stage-0 }

- Согласовать опубликованные порты Compose, порт Vite, `VITE_API_URL`, `DJANGO_ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS` и [инструкцию запуска](getting-started.md). Предложенная схема для хоста: `8071` веб-клиент, `8072` API, `8073` документация. Перед правкой проверить доступность портов на ПК.
- Проверить запуск из чистых примеров окружения. Открыть интерфейс, войти, создать тестовое место и открыть карточку. Повторить с телефона по LAN. В HTTP-режиме проверить ручной выбор точки и понятное состояние геолокации при её недоступности.
- Перед изменениями схемы сделать согласованную копию SQLite штатным способом. Восстановить её в отдельном экземпляре и сверить владельцев, места, чеки, позиции и суммы. Зафиксировать путь рабочей БД и способ восстановления.

**Готово, когда** запуск по инструкции и вход проходят на ПК и телефоне, а тестовый экземпляр поднимается из резервной копии с читаемыми данными.

### 1. Принять каталог и точный расчёт чеков { #stage-1 }

| Порядок | Ветка | Что проверить |
| --- | --- | --- |
| 1 | `feat/place-catalog-controls` | Миграция `0003_place_catalog_fields` на копии SQLite. Категории, избранное, статусы и фильтры. Существующие места и их чеки сохраняются |
| 2 | `feat/receipt-quantity-pricing` | Ветка включает первую по истории. После её merge сверить diff с актуальным `main` и проверить миграцию `0004_checkitem_quantity`, количество, цену за единицу и итог |

Ветка `feat/receipt-item-quantity` содержит альтернативную миграцию `0003_checkitem_quantity` для того же поля. Для последовательного плана принимаем `feat/receipt-quantity-pricing`. Обе реализации количества одновременно создадут конфликт миграций. Если при интеграции возникнет конфликт в этом roadmap, сохранить актуальные этапы и обновить статус после фактического merge.

**Готово, когда** старая позиция получает количество 1, прежняя цена сохраняется как цена за единицу, а `3 × 99,90` даёт `299,70` при сохранении, редактировании и повторном открытии. Сервер вычисляет суммы через `Decimal`, денежные значения передаются десятичными строками. Ветки проходят Jenkins на итоговых SHA и ручную приёмку по [сценариям проекта](testing.md).

### 2. Разделить список и карточку места { #stage-2 }

- Выделить компактный ответ для карты и списка: идентификатор, название, адрес, координаты, поля каталога и отображаемые агрегаты. Карточка получает детали и чеки при открытии. Согласовать новый контракт с React-клиентом и сохранить совместимость нужных API-вызовов.
- Сделать Query Key для списка, карточки и чеков явной частью API-слоя. После создания, редактирования и удаления чека или позиции обновлять связанные представления. При дальнейшем разделении запросов учитывать перемещение чека между двумя местами и кеш каждой стороны.
- Оставить вычисление денежных сумм на сервере. Явно различать сумму визита, средний чек и среднюю цену позиции. При одновременном редактировании полного чека и отдельной позиции определить, как UI узнаёт об устаревших данных.
- Измерить размер ответа и число SQL-запросов на каталоге с накопленной историей. Сохранить фильтрацию по владельцу для списка, деталей и чеков. Проверить переключение аккаунта и очистку данных предыдущего пользователя из кеша.

**Готово, когда** запрос карты не возвращает позиции чеков и не загружает их как отдельные объекты ORM, число запросов не растёт пропорционально количеству мест, а после изменения оценки или цены карта и карточка показывают согласованные результаты.

### 3. Довести повседневную работу на телефоне { #stage-3 }

- Проверить путь от сохранения места до записи повторного визита. Сделать переход между картой, списком и карточкой предсказуемым. Сохранять выбранное место и применённые фильтры при возврате из карточки, где это нужно для продолжения работы.
- Проверить ввод чека с несколькими блюдами, количество, десятичную запятую, необязательную оценку, редактирование и подтверждение удаления. Ошибка сохранения должна оставлять введённые данные и позволять повторить действие.
- Показать понятные состояния при отказе в геолокации, ошибке геокодинга и недоступной подложке карты. При работающем API список сохранённых мест и чеки должны быть доступны независимо от ответа внешнего картографического сервиса.
- После основных сценариев оценить полезность фото блюд и статистики расходов. Для фото сначала определить путь хранения, права, очистку и состав бэкапа. Для статистики проверить вычисления по существующим чекам.

**Готово, когда** с телефона можно добавить место, записать два визита, изменить позицию и найти оба чека. Ошибки сети объясняются интерфейсом, введённые данные сохраняются в форме.

### 4. Закрепить эксплуатацию и личный релиз { #stage-4 }

- Описать согласованный бэкап SQLite, хранение копий отдельно от рабочего файла и восстановление на пустом экземпляре. Для каждого изменения схемы проверять миграцию на копии пользовательских данных.
- Добавить smoke-проверку чистого запуска: загрузка UI, вход, создание тестового места и чтение его чека. В Jenkins проверять код и документацию. LAN-сценарий, мобильный браузер и реальную миграцию проверять на тестовом экземпляре.
- Закрепить настройки запуска для домашней сети, отключить `DEBUG` в рабочем окружении, задать секреты и явные разрешённые хосты. Развести диагностические ошибки запуска, недоступной БД и проблем с внешней картой.
- Оставить SQLite для первой личной версии. Рассматривать PostgreSQL при подтверждённой потребности в серверной синхронизации или конкурентной записи. Если понадобится перенос, сверить пользователей, идентификаторы, связи, суммы и возможность восстановления до переключения.

**Готово, когда** этапы 0-4 проверены на конкретном коммите, приложение поднимается на чистой машине и обновляется с сохранением истории. Восстановленная копия проходит один полный сценарий места и чека.

### 5. Определить границы мобильной версии { #stage-5 }

- На личных выездах проверить, как часто нужно записывать чек без доступа к домашнему API. При подтверждённой потребности зафиксировать отдельное решение о React Native + Expo и локальной SQLite.
- Первый мобильный этап: места, чеки, позиции и оценки локально, перенос существующей истории, экспорт и восстановление. Карта может требовать сети. Сохранённые адреса, координаты и чеки должны быть доступны через список в авиарежиме.
- Определить стабильные идентификаторы, формат денежных сумм и однократный импорт с проверкой количества записей, связей и итогов. Смена основного клиента возможна после проверки импорта и восстановления.
- Синхронизацию нескольких устройств, офлайн-подложку карты, OCR и совместные коллекции планировать отдельными задачами при подтверждённой потребности.

**Готово, когда** принято решение о мобильном сценарии, а для выбранного офлайн-варианта определены данные первого релиза, импорт и проверка восстановления. Детали в [предложении по мобильной архитектуре](mobile-first-proposal.md).

## Как вести работу

Создаём короткие ветки от актуального `main` с учётом зависимостей этапа 1. Тесты и документация меняются вместе с функцией. Проверяем Jenkins на последнем SHA и относящиеся к изменению сценарии из [тестирования](testing.md). Владелец выполняет ручной rebase при необходимости и `merge --no-ff` без PR. После merge проверяем `main` и обновляем статус в roadmap.
