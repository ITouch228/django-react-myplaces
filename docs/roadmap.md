# Дорожная карта MyPlaces

Актуально: 19 ноября 2026 года. Состояние `main` отделено от изменений текущей ветки. Разработка в коротких ветках от актуального `main`, без PR. Rebase и `merge --no-ff` выполняются вручную.

## Цель

Личный журнал заведений с картой, историей посещений, блюдами, чеками и оценками. Главные принципы: сохранность данных, удобство на телефоне, защищённость пользовательских записей, тестируемость.

## Что уже есть в main

| Область | Реализовано | Ограничения |
| --- | --- | --- |
| Авторизация | JWT, регистрация с подсказками, меню аккаунта и выход | Нет управления сессиями и rate limit |
| Карта | Leaflet / OSM, поиск адресов, геолокация, создание и редактирование мест | Нет самостоятельного нативного приложения |
| Мои места | Панель, поиск, сортировка, переход к маркеру, мобильная адаптация | Нет категорий, избранного и статусов до UX-02 |
| Чеки | Посещения, позиции, цены, оценки, редактирование и удаление | Нет количества, фото и расширенной статистики |
| Сервер | Django/DRF, изоляция по владельцу, валидация и SQL-агрегации | Список мест возвращает вложенную историю чеков |
| Хранилище | SQLite и миграции | Нет проверенных резервных копий и восстановления |
| CI | Jenkins на общем агенте, Ruff, mypy, Vitest, TypeScript и MkDocs | Нет полноценного browser E2E и Docker runtime smoke |

## Активная ветка: UX-02

**`feat/place-catalog-controls`**, от `main`. Следующая ветка `feat/receipt-quantity-pricing` создана поверх неё из-за цепочки миграций Django.

Добавляется:
- категория заведения: кафе, ресторан, бар, пекарня, другое;
- статус: «Хочу посетить» или «Посещено»;
- избранное, редактируемое из карточки заведения;
- выбор категории и статуса при создании;
- комбинация фильтров с поиском и сортировкой в панели «Мои места»;
- миграция `0003_place_catalog_fields`, API-тесты и компонентные тесты.

Миграция добавляет поля к существующим местам, не заменяя записи и чеки. Значения для старых мест: `other`, `visited`, `false`.

**Статус:** код в отдельной ветке. До подтверждения Jenkins и ручного merge не считать функциональность частью `main`.

## Текущий этап CHECK-01

Ветка `feat/receipt-quantity-pricing` наследует UX-02 и добавляет количество к позициям чеков, `line_total` и точную сумму чека через Decimal. Цены и суммы в API представлены десятичными строками. Старая цена остаётся ценой за единицу, ранее созданным позициям присваивается количество 1.

**Порядок слияния обязателен:** сначала `feat/place-catalog-controls` (миграция 0003), затем после rebase на обновлённый `main` ветка `feat/receipt-quantity-pricing` (миграция 0004). Обе ветки должны пройти Jenkins на итоговом SHA перед merge. В обоих случаях пользователь самостоятельно делает `merge --no-ff`; PR не создаётся.

## Definition of Done

1. Создать ветку от актуального `main`, без PR и автоматического merge.
2. Изменения API, UI, тестов и MkDocs оформлять в одной ветке.
3. При изменении данных создавать миграции и проверять сохранность существующих записей.
4. Jenkins на последнем SHA: backend, frontend, тесты и `mkdocs build --strict`.
5. Пройти единый [чек-лист](testing.md#перед-merge) на ПК и телефоне.
6. Выполнить rebase на `main`, перепроверить CI, затем вручную `merge --no-ff`.
7. После merge проверить `main`, удалить завершённую ветку и обновить дорожную карту.
